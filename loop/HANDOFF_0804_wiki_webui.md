## 0. 시작하기 전에 — 이미 다 만들어져 있다

**색인·검색·분류·자동주입은 끝났다. 2단계는 그 위에 얹는 열람·관리 화면이다.**
DB를 새로 설계하거나 색인기를 다시 만들지 마라.

```bash
/data/wiki/bin/wiki stats            # 색인 현황
/data/wiki/bin/wiki tree             # 주제 트리 (최상위 4 · 중분류 15 · 잎 50)
/data/wiki/bin/wiki search "유턴"     # 본문 검색 (요약·태그 함께)
/data/wiki/bin/wiki tags Flutter 조사 # 태그 AND
/data/wiki/bin/wiki show <id8> --full # 세션 전문
```

현재 규모: 세션 502건(루트 169 + 서브에이전트 333) · 메시지 45,020건 · 문서 435건 ·
DB 273MB · 요약·태깅 167/167(100%) · 태그 67종.

| 파일 | 역할 |
|---|---|
| `bin/wiki_db.py` | 스키마 단일 소스. `connect()` / `init()`(열 추가 마이그레이션 포함) |
| `bin/wiki-index` | 증분 색인기. flock 단일 인스턴스. SessionEnd 훅 + cron이 부른다 |
| `bin/wiki` | 조회 CLI — **웹 API가 흉내낼 쿼리들이 여기 다 있다** |
| `bin/wiki-tree` | `tree.yaml` → DB 투영(`apply`) + 항목 배치(`assign`) + `audit` |
| `bin/wiki-enrich` | `claude -p` 요약·태깅 백필, Obsidian 노트 생성 |
| `bin/wiki-context` | SessionStart 훅이 부르는 목차 생성기 |
| `bin/redact.py` | 비밀정보 마스킹 + 스크럽 |
| `tree.yaml` | **주제 트리의 단일 소스.** DB의 nodes/items는 이것의 투영일 뿐 |
| `tags.yaml` | 태그 통제 어휘 79개 |

## 2. 2단계 범위 (마스터가 원래 요구한 것 중 웹UI에 해당하는 부분)

| # | 요구 | 지금 상태 | 2단계에서 할 일 |
|---|---|---|---|
| 1 | 어디서든 트리 확인 | CLI만 | **웹 화면** |
| 2 | 세션 관리(추가·삭제·재배치) | CLI에 없음 | **편집 UI** |
| 3 | 키워드 검색 | ✅ CLI | 웹 검색창 |
| 4 | 태그 중복·통합검색 | ✅ CLI | 태그 칩 UI |
| 5 | 신규 세션 자동 등록 | ✅ 훅+cron | (그대로) |
| 6 | Claude 자동 참조 | ✅ SessionStart 훅 | (그대로) |
| 7 | 타 LLM 통합 | 미착수 | **3단계** |

"세션 추가·삭제"의 실제 의미를 오해하지 마라:
- **추가** = 세션은 훅이 자동 등록한다. 웹에서 할 일은 *항목을 노드에 수동 배치*다.
- **삭제** = `sessions.hidden=1` 소프트 삭제. **원본 jsonl은 절대 지우지 마라.**
  DB는 언제든 재생성 가능한 파생 색인이라는 게 이 시스템의 대전제다.
- **재배치** = `tree.yaml`을 고치고 `wiki-tree apply && wiki-tree assign`.

## 3. 반드시 지켜야 할 설계 제약 (어기면 조용히 망가진다)

### 3-1. `tree.yaml`이 단일 소스다
`apply`는 nodes/items를 **지우고 다시 만든다**(노드 id가 매번 바뀐다).
그래서 사람·LLM의 판단은 id가 아니라 **문자열**로 남겨야 살아남는다:
- LLM 분류 → `sessions.topic_path` ("중분류/소분류")
- 태그 → `item_tags` (노드와 무관)

웹에서 재배치를 구현할 때 **DB의 nodes를 직접 고치지 마라.** `tree.yaml`을 쓰고
`apply`+`assign`을 돌려라(1초 안 걸린다). 수동 배치를 영속화하려면
`topic_path`처럼 **문자열 기반 오버레이 테이블**을 새로 만들어야 한다.

### 3-2. 파서는 관대하면 안 된다
`tree.yaml`은 자체 제작 파서(`wiki_tree_lib.load_tree`)로 읽는다. 탭 들여쓰기와
같은 부모 밑 동명 노드는 **즉시 실패**시키게 해뒀다(조용히 트리가 재편되던 버그).
웹에서 YAML을 생성할 때 이 규칙을 깨지 마라.

### 3-3. 쓰기는 반드시 락을 거쳐라
`wiki-index`는 flock 단일 인스턴스다(`/tmp/wiki-index.lock`). SessionEnd 훅이
세션마다 부르고 cron이 20분마다 부른다. 웹 서버가 DB에 쓸 거면 같은 락을 쓰거나,
**읽기 전용으로 두고 쓰기는 CLI에 위임**하는 편이 안전하다.

### 3-4. 절대 하지 말 것
- `~/.claude/projects/` 수정 — 원본 아카이브다. 읽기만.
- `wiki-index --reset` / `--full`, `wiki-enrich run --force` — 재생성에 20분+ 든다.
- `git add -A` — 동시 세션이 브랜치를 공유한다. 파일명 지정해서 스테이징.

## 4. 권장 구현안 (판단은 새 세션이 하되, 근거는 남겨라)

**기존 자산 재사용을 우선한다**(마스터 선호 — 새 의존성보다 기존 패턴).

- **백엔드**: 파이썬. 지금 `/data/wiki`는 **표준 라이브러리만** 쓴다(sqlite3 외 의존성 0).
  FastAPI를 쓸 거면 venv + systemd 서비스가 늘어난다는 걸 감안하고, 그만한 값어치가
  있는지 먼저 판단해라. 화면이 몇 개 안 되면 `http.server`로도 된다.
- **프런트**: 단일 페이지. 좌측 트리 / 우측 트랜스크립트 / 상단 검색·태그칩.
  빌드 도구 없이 순수 HTML+JS를 권한다(빌드 파이프라인이 생기면 유지비가 붙는다).
- **API는 `bin/wiki`의 쿼리를 그대로 옮기면 된다** — 이미 검증된 SQL이다.
  특히 한국어 검색의 **2글자 LIKE 폴백**(FTS5 trigram이 3글자 미만을 못 받는다)을
  빠뜨리지 마라. "유턴"·"지도"가 0건이 된다.
- **포트**: 8025 근방이 비어 있다(8002/8003/8014/8080/8081/8082/8501 사용 중).
- **노출**: `n8n_cloudflared`는 **토큰 방식 원격 관리 터널**이다. 로컬에 config.yml이
  없으므로 **Cloudflare 대시보드에서 public hostname을 추가해야 한다 — 마스터 수동 작업.**
  `tiles/valhalla/navi.westinx.com`도 같은 방식이고 로컬 nginx를 안 거친다
  (`docker/INFRA.md` 확인). 로컬 nginx conf는 `n8n.westinx.com` 하나뿐이다.
