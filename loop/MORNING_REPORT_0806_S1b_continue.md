## 핵심 발견 1 — 조사 전제가 세션 도중 무너졌다

세션 시작 시 기기에 깔려 있던 빌드가 **S3b 이전**(`lastUpdateTime` 2026-08-05 20:40)이었다.
그런데 이전 세션이 ECONNRESET로 끊긴 사이 **별도 세션**이 `2ffd233`/`7e68a72`로
**시스템 PIP를 완전히 폐기하고 `SYSTEM_ALERT_WINDOW` 플로팅 오버레이로 교체**해
놓은 상태였다([MORNING_REPORT_0806_S3b_floating_and_notif.md](MORNING_REPORT_0806_S3b_floating_and_notif.md)).
이 핸드오프의 지시(§2-1~2-4, PIP 반복 왕복)는 전부 **S3에서 이미 고쳐진 트리거**
(`inactive` 오검출 → PIP 진입)를 대상으로 한 것이었다.

판단: 낡은 전제로 계속 조사하는 대신 **현 HEAD로 재빌드해 재검증**했다(JDK21,
`adb install -r`로 앱 데이터 보존 확인).

## 핵심 발견 2 — "M32에서 재현 안 됨"을 "해결됨"으로 잘못 읽었다 (마스터 정정)

아래 재검증 결과를 처음엔 "무결함"으로 보고했는데 **틀렸다.** **M32는 마스터의
실사용 폰이 아니라 유루나비 전용 공기계다** — 서버와 같은 WiFi에만 물려 있고
5G/LTE 실통신이 없으며 설치 앱·백그라운드 동작이 거의 없다. 실제 장애는 실도로
주행 + 실제 셀룰러망 + 그 폰에 평소 깔린 앱들의 백그라운드 경쟁 속에서 일어나며,
앱 개수/백그라운드 점유가 클수록 심해진다(마스터 증거: 앱이 적고 백그라운드를
최소화한 개인폰 갤럭시 A34가 최신 갤럭시 플립7보다 오래 버팀). → 마스터 지시:
M32로 환경을 흉내 내려 하지 말고 **앱 자체의 메모리·비디오 메모리(GPU 메모리)
사용량 — 용량·점유율·점유시간·효율성**을 감사하라. 이어서 진행했다(아래
"핵심 발견 3").

## 재검증 결과

- **노티피케이션 트리거(구 버그)**: 현 HEAD에서 완전 무반응 확인 — S3의 "라이프사이클
  오검출 근원 제거" 수정이 실기기에서 검증됨.
- **실제 트리거(HOME 키 → 오버레이 표시 → 아이콘 1탭 복귀)**: 단발 1회 + 반복 15회
  + 장기체류(2분20초) 1회 = **17회 왕복 전부 백화 없음.** `onMapCreated`는 최초
  진입 1회만 호출되고 이후 재호출 0건, `MissingPluginException` 0건.
- **§3 가드 결함**(`_locLayerReady`/`_destLayerReady` 미리셋)은 코드에 **여전히 존재**하지만,
  그걸 발현시키던 유일한 확인 경로(PIP 진입 시 윈도우 리사이즈→네이티브 서피스 파괴)가
  S3b에서 메커니즘째 사라져 **실질적으로 트리거 불가 상태**가 됐다. "고쳤다"가 아니라
  "트리거가 없어졌다"는 것 — 근본 수정(가드 리셋)은 여전히 권장 사항으로 남는다.
- **속도계·일출일몰 축**: 같은 17회 전부 무결함. 별도로, 반복 중 카메라 접근 경고
  게이지(로드맵 18번)가 실제 발동해 속도계 자리를 대신 채운 것을 백화로 오인할 뻔했다 —
  확인 결과 정상 동작이었다.
- **메모리 압박 축**: `am send-trim-memory`가 4회 전부 OS에 의해 거부됨
  (`foreground process에는 background trim level을 설정할 수 없다`) — `NavForegroundService`가
  살아있는 한 강제 trim 대상이 아니라는 뜻. 진짜 압박(다수 실앱 백그라운드)은 M32가
  전용 공기계라 앱이 거의 없어 시도할 수 없었다.
- **[범위 밖 신규 발견]** `StreamSink is bound to a stream` 크래시 1건 관측(HOME 복귀 후
  ~1분37초). 재현조건 미확정, 원인 미조사 — 다음 세션 후보로 남김.

## 핵심 발견 3 — 메모리·GPU 메모리 감사 (마스터 지시 반영)

**정적 코드 감사**: `StreamController`/`AnimationController`/`Timer` 등 Dart 레벨
리소스는 전수 확인 결과 전부 정상 해제됨(누수 없음). `maplibre_gl` 플러그인 자체도
Flutter 엔진의 알려진 플랫폼뷰 서피스 누수 버그([flutter/flutter#107297](https://github.com/flutter/flutter/issues/107297))를
자체 우회 코드로 이미 막아뒀다(`destroyMapViewIfNecessary()`가 `removeView`+`onDestroy`를
명시적으로 호출).

**16분 vGPS 주행 중 GPU 메모리(`EGL/GL mtrack`) 30초 간격 실측** (`loop/repro_s1b/sample.sh`,
원본 `loop/repro_s1b/mem_gpu_samples_0806.csv`):
- 정상 주행 중(274초 구간)은 **완전 평탄** — 1Hz 위치 갱신 자체는 GPU 메모리를 갉아먹지 않음
- 재탐색(reroute) 1건 발생 순간과 정확히 겹쳐 `GL mtrack`이 **+22.5MB 튀는 것**을 발견,
  "재탐색마다 새는가?" 의심 → **같은 세션에서 수동 재탐색 3회 연속 실행해 직접 검증**:
  추가 3회에서는 **증가 없음(±300KB 잡음 수준)**. → 재탐색마다 반복되는 누수가 아니라
  **첫 재탐색에서 GL 버텍스 버퍼가 새 상한으로 한 번 커진 뒤 재사용하는 정상 동작**으로
  판정(대부분의 GL 렌더링 엔진에 흔한 최적화, 결함 아님).
- **결론(이번 세션 표본 한계 내)**: 16분·재탐색 4회 규모에서는 GPU 메모리 단조 증가
  (누수) 징후를 찾지 못했다. 단, 표본이 작아 **10시간·수십 회 재탐색 규모에서도
  안전하다는 뜻은 아니다** — 다음 세션에서 표본을 키워야 한다(§11-6).
- 부수 발견: 디스크 타일 캐시(500MB, `map_cache_provider.dart`) / 타일 1.65GB(S2가
  미측정으로 남긴 것) / GPU 텍스처 캐시(이번에 측정한 ~180MB)는 **서로 다른 세 캐시
  시스템**이다 — 혼동 주의.

상세: [RECON_0805_render_resource.md](RECON_0805_render_resource.md) §11.
