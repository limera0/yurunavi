## 2. 왜 이렇게 되나 — 원리

**git 인덱스(staging area)는 워킹트리당 하나, 즉 `.git/index` 파일 하나다.**
프로세스별·세션별로 분리되지 않는다. 세션 A가 `git add`한 내용은 **세션 B의
`git commit`에 그대로 딸려간다.** 브랜치가 같은지 여부와 무관하다 — 같은
워킹트리를 공유하면 무조건 그렇다.

`git commit -a`도 동일한 사고를 낸다. 추적 중인 모든 변경 파일을 자동 스테이징하므로
다른 세션이 편집 중인 파일까지 쓸어간다.

## 3. 피해 범위 — 이번엔 없었다

- `git diff bd57885 -- <세 파일>`이 **빈 diff** → 커밋된 내용은 S2 세션이 작성한 그대로.
- 코드 손실·오염·중복 없음. `flutter analyze` 0건 / `flutter test` 전건 통과로 재확인.
- **유일한 피해는 히스토리 가독성**이다. 커밋 메시지가 S1b 문서 작업을 말하는데
  내용물엔 S2 코드가 들어 있어, `git log`나 `git blame`으로 "이 코드가 왜 들어왔나"를
  추적하면 엉뚱한 맥락이 나온다.

**히스토리는 고치지 않았다.** 공유 브랜치에서 `reset`/`rebase`/force push는
다른 세션의 작업을 날릴 수 있는 파괴적 조작이라 CLAUDE.md 하드룰 위반이다.
잘못된 메시지를 남겨두고 기록으로 보완하는 쪽이 안전하다.

## 4. 재발 방지 규칙 (CLAUDE.md 하드룰에 반영됨)

1. **`git add -A` / `git add .` / `git commit -a` 절대 금지.** 파일명 명시만.
2. **커밋 직전 `git status --short`로 스테이징 목록 확인.** 내가 안 건드린 파일이
   올라가 있으면 `git restore --staged <그 파일>`로 내리고 커밋한다.
   "이미 올라와 있으니 같이 커밋" 절대 금지 — 그게 이 사고다.
3. **스테이징과 커밋을 한 호흡에** — `git add <files> && git commit …`.
   `add` 후 다른 작업(빌드·테스트·에이전트 대기)을 하고 나중에 커밋하면 그 사이에
   다른 세션이 훔쳐갈 창이 열린다. 이번 사고가 정확히 그 창에서 났다.
4. **꼬였으면 되돌리지 말고 기록한다.** 보고서 + 체크리스트에 어느 커밋에 무엇이
   섞였는지 남긴다.

## 5. 근본 대책 후보 (미채택 — 마스터 판단 필요)

| 방안 | 장점 | 단점 |
|---|---|---|
| **세션별 git worktree** (`git worktree add`) | 인덱스가 물리적으로 분리돼 사고가 **구조적으로 불가능**해진다 | 워크트리마다 빌드 캐시(`build/`, `.dart_tool/`)가 따로 생겨 디스크·빌드시간 증가 |
| 동시 세션 금지(직렬화) | 가장 단순 | 야간 자동화 체인 처리량이 떨어진다 |
| 커밋 전 스테이징 검증 훅 | 자동 차단 | 훅이 "내 파일"을 알 방법이 없어 판정 불가 — 실효성 낮음 |
| 현행(규칙 준수) | 비용 0 | 규칙을 어기는 세션 하나로 다시 발생 |

> 유일한 구조적 해법**이다. 규칙은 이번처럼 한 세션만 어겨도 뚫린다.

> **재발 빈도를 한 번 더 보고 결정**하는 것도 합리적이다.
