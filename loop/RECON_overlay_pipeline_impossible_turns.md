# RECON — 불가능한 좌회전 2건, 그래프 레벨 원인 규명 + 로컬 오버레이 파이프라인 (2026-07-20)

대상: `loop/RECON_impossible_left_turns.md`가 남긴 2개 지점. 마스터가 두 곳 모두 직접
주행하며 확인(중앙분리대 있음, 좌회전 원천금지)한 뒤 "1번은 정식 오버레이 파이프라인으로,
2번은 좌회전 금지 처리"로 방향 확정. 이 문서는 그 후속 — 원인을 way/node 단위까지
정확히 규명하고, 격리 환경에서 patch를 만들어 검증한 뒤, 재사용 가능한 파이프라인으로
정리한 기록이다.

## 0. 앞단: 앱 안전망 (커밋 `8a4ee60`)

그래프 패치보다 먼저, `lib/services/routing_service.dart`에 `knownImpossibleTurnAvoids`
(두 지점 좌표) 상수를 추가해 모든 `/route` 요청에 `avoid_locations`로 포함시켰다.
하드 차단이 아니라 페널티라 완벽하진 않지만 그래프 패치가 나올 때까지의 즉시 안전망.
flutter-coder 구현 + code-auditor PASS 후 커밋 완료, 283/283 테스트 통과.

## 1. 삼봉로/삼남로 (37.09172, 127.09205) — 원인: way 하나가 분리대를 관통

프로덕션 pbf(`/data/valhalla/custom_files/south-korea-latest.osm.pbf`, 2026-06-01
스냅샷)를 `osmium extract`로 직접 열어 확인. Overpass API는 이번에도 406 에러로
접근 불가(RECON_songtan_paldang_uturn.md §5와 동일 증상, 원인 미상 — 우리 pbf를
직접 여는 방식으로 완전히 우회 가능했음).

**정확한 구조**: 무명 주택가 도로 `way 970139442`(highway=residential, 12개 노드)가
삼봉로의 두 편도 차로 — `way 813377254`(근접 차로)와 `way 819321926`(원거리 차로,
분리대 반대편) — 를 노드 하나씩(`8977582048` / `8977582047`, 두 노드 간 거리 약 12m)
사이에 두고 그대로 관통하도록 매핑되어 있었다. 좌표를 지도로 그려 직접 확인
(아래 첨부 이미지 대응, 세션 아티팩트 참조): 골목이 근접 차로를 지나 계속 이어져
원거리 차로까지 뚫려 있는 모양 — 실제로는 중앙분리대가 막고 있는 자리.

**패치**: `way 970139442`를 정확히 그 12m 구간(`8977582047`↔`8977582048`)에서 분리해
별도 way(임시 id `9970139442`)로 만들고, 그 구간에만 `motor_vehicle=no`+`motorcycle=no`
태그(`RECON_gate_avoid_poc.md`에서 실측 검증된, 이 Valhalla 빌드에서 실제로 작동하는
조합 — `access=private`는 무효였음을 그때 확인함). 나머지 구간(근접 차로 접점 및 그
아래 주택가 전체)은 원래 태그·id 그대로 유지.

**격리 검증** (`/data/valhalla/poc_impossible_turn/`, 프로덕션 무변경):
| | before | after |
|---|---|---|
| 관통 지점 직통 (n047→n048) | **0.01km** "Drive south" — 유령 관통 | **0.467km** 삼남로 교차로까지 가서 좌회전→유턴→우회전 — 실제 우회 |
| 주택가 남쪽(500m)→근접 차로 회귀 테스트 | 0.496km | 0.496km (동일, 회귀 없음) |

## 2. 밀머리로/동부대로 (37.13696, 127.07838) — 원인: 왕복도로가 북행 차로와 노드 공유

반경을 넓혀 조사(bbox 약 1km²)한 결과 **80개 이상의 way로 이루어진 복합 입체교차
구간**임을 확인 — secondary_link 연결로 6개, 부분적으로 `oneway=no`가 섞인 구간 3개,
지하주차장(`parking_aisle`+`tunnel=yes`)까지 겹쳐 있었다(원 RECON 문서의 "복합
분기점" 추정과 일치). 이 규모에서 pt1처럼 섣불리 "여기만 자르면 된다"고 단정하는
건 위험 판단이라 최초엔 보류했으나, 마스터가 실주행 경험으로 "좌회전 금지 처리"를
명확히 지시해 아래와 같이 처리.

**정확한 구조**: 밀머리로(`way 37404818`, 왕복, 32개 노드)가 동부대로 북행 차로의
시작 노드(`node 7811891565`)와 **정확히 같은 지점**을 공유한다 — 이 노드에서
`way 837782045`(남쪽에서 도착)가 끝나고 `way 837782046`(북쪽으로 출발)이 시작된다.
남행 차로(`way 835287175`)는 같은 위도에서 약 11m 서쪽의 다른 노드(`571374364`,
이 역시 밀머리로가 바로 다음 순번으로 지나가는 노드)를 지난다 — 즉 밀머리로가
중앙분리대로 갈라진 두 차로 사이를 그대로 관통하며 각 차로와 노드를 공유하는,
pt1과 본질적으로 같은 종류의 문제. 신고 좌표(37.13696,127.07838)는 이 공유 노드
`7811891565`에서 8m 이내로, 북행 차로 쪽 진입이 신고된 지점과 정확히 일치한다.

**패치**: way 분할이 아니라 OSM 표준 `type=restriction`+`restriction=no_left_turn`
관계 추가 — `from=way 37404818`(밀머리로), `via=node 7811891565`, `to=way 837782046`
(북행 차로). Valhalla mjolnir의 `restrictionbuilder.cc`/`complexrestrictionbuilder.cc`는
이 fork의 커스텀 패치(모터사이클 costing/회전각 튜닝)와 무관한 stock 기능이라 별도
검증 없이도 동작할 것으로 예상했고, 실측으로 확인됨.

**격리 검증**:
| | before | after |
|---|---|---|
| 밀머리로→동부대로 북행 직통 | **0.436km** "Turn right onto 동부대로" — 유령 좌회전(중앙분리대 무시) | **1.023km** 남부대로 경유 실제 우회 |
| 밀머리로 직진(회전 없음) 회귀 테스트 | 0.06km | 0.06km (동일, 회귀 없음) |

## 3. 오버레이 파이프라인 (`docker/impossible_turn_overlays/`)

`RECON_overlay_pipeline.md`(2026-07-02, 사유지 회피용으로 설계만 하고 미구현)의
설계를 확장·구현. 사유지 케이스와 다른 점: 그건 "폴리곤 안의 아무 도로"에 태그를
붙이는 동질적 작업이라 매 pbf 갱신마다 id를 새로 찾는 폴리곤 기반 재탐색이
가능했지만, 이번 두 건은 way 분할·relation 추가처럼 **정확히 이 노드/이 way**를
지목해야 하는 이질적 작업이라 그 방식을 그대로 쓸 수 없다. 대신:

- `manifest.yaml` — 오버레이별 `.osc` 경로, 근거 노드/way id + 좌표, target/regression
  테스트 임계값을 선언.
- `apply_overlays.py` — ①`osmium getid --verbose-ids`로 근거 id가 여전히 존재하고
  좌표가 기록값과 5m 이내인지 확인(매퍼가 재작도했으면 여기서 중단하고 사람이
  `.osc`를 다시 만들어야 함) ②`osmium apply-changes`+`sort`로 패치 적용
  ③격리 `tile_dir`에 `valhalla_build_tiles` 실행(프로덕션과 동일 이미지·config,
  경로만 격리) ④임시 포트 컨테이너로 target/regression 자동 검증. **프로덕션
  pbf/tile_dir/컨테이너는 어떤 단계에서도 건드리지 않음.**
- `swap_production_tiles.sh` — 실제 반영 전용 별도 스크립트(`--yes-i-am-sure` 필수).
  타일뿐 아니라 `tile_extract`(.tar, `valhalla_build_extract`로 재생성 — 프로덕션
  config가 tile_dir과 tile_extract를 모두 참조하고 있어 tile_dir만 바꾸면 반영 안
  됨을 미리 확인해 반영)까지 함께 스왑하고, 스왑 직후 프로덕션 8002에 직접
  curl 자동 검증 → 실패 시 타임스탬프 백업으로 자동 롤백.

**파이프라인 자체 검증**: `apply_overlays.py`를 프로덕션 pbf 스냅샷에 대해
korea-only(94초 빌드)와 korea+japan(프로덕션과 동일 구성) 두 모드로 실행 —
둘 다 위 표의 격리 PoC 수치를 그대로 재현하며 PASS. **아직 프로덕션에는 반영하지
않음** — `swap_production_tiles.sh` 실행은 마스터 최종 확인 후.
