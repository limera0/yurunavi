### P0. POI가 홈/내비 화면 모두 안 뜸 — **확진: 최근 빌드들이 서비스키 없이 빌드됨**

**사용자 보고**: 홈 화면·내비 화면 둘 다 POI 아이콘이 전혀 안 뜸. 카페 필터 검증도 이것
때문에 불가능했음.

**원인 추적 결과**:
- `poi_service.dart:18` — `SEMAS_SERVICE_KEY`는 컴파일타임 주입
  (`String.fromEnvironment`), 빌드 시 `--dart-define-from-file=env.json` 플래그가 있어야
  실제 값이 들어감. 코드 주석에 이미 "analyze/test 시엔 빈 문자열이 정상"이라고 명시돼
  있음 — 즉 **실기기용 빌드에선 반드시 이 플래그가 있어야 한다는 뜻**.
- `RIDE_RESULTS_0714.md`에 기록된 **모든** `flutter build apk --debug` 호출(4회)이 이
  플래그 없이 실행됨. 오늘 아침 내가 검증 빌드를 만들 때도 똑같이 플래그를 빠뜨렸음
  (스모크테스트용이라 무해했지만, 같은 실수가 반복되는 패턴 자체가 문제).
- 라이브 검증: 빈 `serviceKey`로 실제 API(`storeListInRadius`)를 curl로 호출하면
  **HTTP 401 `Unauthorized`**(JSON도 아닌 순수 텍스트)가 돌아옴 — `_fetchOne()`의
  `if (resp.statusCode != 200) return [];` 분기가 **어떤 로그도 남기지 않고** 조용히
  빈 리스트를 반환함(예외가 아니라 상태코드 분기라 기존 `catch`의 `debugPrint`도 안 탐).
  오늘 로그에 POI 관련 줄이 단 한 줄도 없는 것과 정확히 일치.
- **왜 07-14 테스트 땐 POI가 (오염된 채로나마) 보였는가?**: 07-14 라이딩은 07-14 세션의
  코드 수정이 반영되기 *이전* 빌드로 진행됐음(그 세션 자체가 "전날 밤 빌드로 테스트"
  구조라 실제로는 07-13 이전 빌드 — 그때는 플래그가 있었거나 다른 경로로 키가 살아있었던
  것으로 추정). 07-14 세션에서 아이콘 렌더러 공유 추출 등 코드를 고치고 **플래그 없이
  재빌드**한 게 이번에 실제 폰에 깔린 빌드 — 그 이후로 계속 깨져있었던 것.

**결론**: 코드 로직 버그가 아니라 **빌드 절차 실수가 반복되는 것 자체가 근본 문제**임.

### P1. 고가/터널 안내(19번) — "우측 출구"만 나옴, "고가도로 구간입니다" 문구가 아예 없음

**원인**: 로그 전체에서 `YNAV_STRUCT zones=0`이 **경로가 몇 번을 바뀌어도(7개 서로 다른
라우트) 단 한 번도 예외 없이** 0으로 찍힘. 사용자가 실제로 들은 "우측 출구"는
`exit_approach_landmark`/`exit_imminent_landmark`(고속도로 출구 랜드마크 안내, 완전히
별개의 기존 기능) 이벤트였음 — 신규 구조물(bridge/tunnel) 안내는 애초에 한 번도
발화하지 않음.
- **확인 불가능한 이유**: `fetchStructureZones()`의 실패 분기(상태코드 이상/예외)는
  `dev.log()`로만 남기는데, 이건 `debugPrint`를 가로채는 파일 로거에 안 잡힘(POI와 같은
  종류의 사각지대). 그래서 이게 "이 경로엔 진짜 다리/터널이 100m 이상 없었다"인지
  "API 호출 자체가 실패하고 있다"인지 로그로 구분이 안 됨.
- 실측 재현 시도: `valhalla.westinx.com`에 실제 도로 구간 두 곳으로 `/route`→`/trace_attributes`
  체이닝을 직접 재현해봤으나 이번엔 bridge/tunnel이 안 걸리는 구간을 뽑았을 가능성이 있어
  결론을 못 냄(정확한 실측 좌표를 다시 찾아야 함).
- **결정한 조치**: 우선 로깅부터 고쳐서 다음 라이딩에서 진짜 원인을 알 수 있게 만든다
  (POI와 동일 패턴 — 실패 분기에 `debugPrint('YNAV_STRUCT_ERR ...')` 추가).

### P1. 경유지 통과 시 카드/TTS가 "목적지"라고 나옴

**원인 확정**: `nav_screen.dart`의 `_TurnStep._labelForType()`이 Valhalla maneuver
type 4/5/6(각 세그먼트의 끝)을 무조건 `'목적지 도착'`으로 매핑함 — 이 앱은 경유지마다
별도 서브 라우트로 갈아타는 구조라(P0-B 참조) **경유지 구간의 끝도 그 세그먼트
입장에서는 type 4/5/6으로 나옴**. `_passedWaypointCount >= widget.waypoints.length`
여부(이미 도착배너 게이팅에 쓰고 있는 바로 그 조건)를 전달받지 않아서 항상 최종 목적지
취급함.
- 같은 원인이 TTS에도 있음: `voice_engine.dart`의 `eventForType()`도 type 4/5/6을
  `'destination'` 이벤트로만 매핑하고, `default_ko.json`의 `destination_approach`/
  `destination_imminent` 템플릿이 "목적지"를 하드코딩(`"{dist}미터 앞 목적지"`) — 경유지
  구간에서도 그대로 발화됨. (참고: P0-B의 지오펜스 기반 "경유지 도착/통과" 음성은 이것과
  별개의 정상 동작 중인 시스템 — 그건 잘 나왔다고 사용자가 확인함. 문제는 이 턴바이턴
  거리기반 시스템 쪽.)

### P2. 재탐색 화면 카메라가 마지막 주행 방향으로 고정됨 (신규)

**원인**: `nav_screen.dart:_openCourseSheet()`가 `CameraUpdate.newLatLngBounds(...)`만
호출함 — 이 API는 위치/줌만 맞추고 **bearing(회전)은 건드리지 않아서** 내비 중 회전된
지도 방향이 그대로 유지됨. `maplibre_gl_platform_interface`에 `CameraUpdate.bearingTo(double)`
가 이미 존재하므로 bounds fit 뒤에 이어서 호출하면 됨.
