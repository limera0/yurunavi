## ▶ 근본원인 확정 + 수정 완료 항목

### 6-부분. 구조물(고가/터널) API 호출이 `400`으로 실패

**원인**: `docker logs yurunavi-valhalla`에서 실측 확인 —
```
400::Exact route match algorithm failed to find path: edge_walk algorithm
failed to find exact route match. Try using shape_match:'walk_or_snap' to
fallback to map-matching algorithm
```
`fetchStructureZones()`가 `shape_match: 'edge_walk'`를 쓰는데, 이 모드는 경로 shape가
그래프 엣지와 **정확히** 일치해야만 성공한다(부동소수점 오차·교차로 밀집 구간에서 흔히
깨짐). Valhalla 에러 메시지가 직접 대안을 알려줌.

**수정**: `shape_match: 'walk_or_snap'`으로 교체(`routing_service.dart`) — edge_walk를
우선 시도하되 실패하면 자동으로 map-matching 폴백. 이 호출은 이미 20초 타임아웃+실패 시
빈 리스트 반환 계약이라 리스크 낮음.

**참고**: 전체 라이딩 동안 이 호출은 22회 중 1회만 400이었음(나머지는 200, 1~10KB 응답).
즉 "항상 실패"는 아니었음 — 아래 6-잔여 참조.

### 7. 경유지 통과 안내가 도달 전에 먼저 나옴

**원인**: `_checkWaypointProgress`가 GPS 위치가 40m 지오펜스 안에 들어오는 **즉시**
"통과" 이벤트를 발화 — 정차 여부만 도착/통과 문구를 갈랐을 뿐, 실제로 지나쳤는지는
전혀 보지 않았음. 사용자가 경유지 정확히 앞에 정차했는데도 정차 전에 이미 "통과했다"고
나온 것과 정확히 일치.

**수정**: 순수 함수 `waypointPassageEvent()`를 추출(`exitGateOpen()`과 동일 패턴,
테스트 분리용). 지오펜스 안에서 관측된 **최근접 거리**를 추적하다가, 그 최근접점보다
10m(`_kWaypointPassedMarginM`) 이상 멀어져야 "통과"로 판정. 정차 시(속도 ≤8km/h)엔
기존처럼 즉시 "도착" — 이동하며 지나치는 경우만 판정 방식이 바뀜.
`test/waypoint_passage_test.dart` 9개 케이스 추가(접근 중 미발화, 경계값, 실제
시퀀스 시뮬레이션 포함).

### 10. 목적지 도착도 "경유지 도착"이라고 나옴

**원인**: 지난 세션(`957974e`)이 "경유지 구간도 목적지라고 나오는" 버그를 고치면서,
`isFinalDestination` 플래그를 `_passedWaypointCount >= widget.waypoints.length`로
**경로 로드 시점 한 번만** 계산해 전체 maneuver 리스트에 **일괄 적용**해버렸음. 경유지가
1개 이상 있으면 경로 로드 시점엔 `_passedWaypointCount=0`이라 이 값은 항상 false —
그런데 Valhalla는 각 레그(경유지별 구간)가 끝날 때마다 도착(type 4/5/6) maneuver를
하나씩 내고 `_collectManeuvers`가 이걸 그대로 이어붙이므로, **리스트의 마지막
maneuver(=진짜 최종 목적지)까지 포함해 전부 다** "경유지"로 잘못 라벨링됐음. 즉 이전
버그(경유지가 목적지라고 나옴)를 고치다가 반대 버그(목적지가 경유지라고 나옴)를 만든
것.

**수정**: `_applyRouteGuidance`(카드 라벨)와 `_handleVoice`(TTS `dest_word`) 둘 다
실시간 진행 상태가 아니라 **maneuver 리스트 상 위치**로 판정하도록 변경 — "이 maneuver가
리스트의 마지막 항목인가"만 보면 됨(Valhalla 다중 레그 경로는 항상 마지막 maneuver가
진짜 최종 목적지이므로). `_passedWaypointCount`의 원래 용도(재탐색 시 이미 통과한
경유지 배제, 도착배너 게이팅)는 그대로 유지.

### 3. 지도 팬/줌 시 POI가 "랜덤하게" 바뀜

**원인**: `selectForAmbientDisplay`의 그리드 셀 경계가 **현재 뷰포트 경계(south/west)에
상대적**으로 계산됐음(`(poi.lat - south) / latSpan * gridSize`). 함수 자체엔 무작위
요소가 전혀 없지만, 팬으로 뷰포트가 조금만 움직여도 그리드 원점이 같이 움직여 동일한
POI 집합인데도 매번 다른 셀에 배정되고, 그 결과 4x4 라운드로빈에서 살아남는 POI가
호출마다 바뀜 — "편의점이 사라지고 식당이 뜬다"는 체감과 일치.

**수정**: 셀 배정을 절대좌표 기준(`floor(poi.lat / cellLatSize)`, 뷰포트 오프셋 없음)으로
바꾸고, 셀 크기 자체도 1-2-5 스텝(`_snapCellSizeDeg`)으로 스냅해 뷰포트 span의
부동소수점 미세 흔들림도 흡수. `test/services/poi_service_test.dart`에 팬 안정성
회귀 테스트 추가 — 스냅 적용 전 버전으로는 실제로 실패함을 확인(code-auditor가 별도
시뮬레이션으로 재검증).

## ▶ 근본원인 가설만 있음 (코드 수정 보류 — 근거 부족)

### 6-잔여. 구조물 API는 대부분 성공(200)하는데도 "우측 출구"만 들림

`400` 수정은 22번 중 1번짜리 예외 케이스만 해결한다. 나머지 21번은 이미 200으로
성공했는데도(응답 크기 1~10KB, 실제 엣지 데이터 포함) 여전히 "고가도로 진입"/"터널
진입" 안내를 들었다는 보고는 없음(참고: `RIDE_RESULTS_0715.md`에서도 "고속도로 출구
랜드마크 안내(`exit_approach_landmark`)는 별개 기능이고, 신규 구조물 안내는 그 라이딩
내내 한 번도 발화하지 않았다"고 이미 확인된 바 있음).

**유력 가설**: `buildStructureZones()`의 `minLengthM = 100` — 이어붙인 bridge/tunnel
엣지 합산 길이가 100m 미만이면 그 구간은 통째로 버려짐. 한국 도심 고가/지하차도는 교차로
하나 분량(수십 m)인 경우가 흔해서, 실제로 그 아래/위를 지나가고도 zone 자체가 생성 안
됐을 가능성이 있음.

**왜 지금 안 고쳤는지**: 실제로 통과한 구조물들의 길이 분포를 모른 채 임계값을 낮추면
반대로 사소한 육교·박스컬버트까지 매번 안내해 오히려 거슬릴 수 있음(과교정 위험).

**다음 라이딩에서 확인할 것**: `grep 'YNAV_STRUCT zones='` 결과가 0인지 아닌지, 그리고
0이 아니라면 실제로 성공한 구조물 안내가 있었는지 여부.

### 9. 급커브 안내가 전혀 안 나옴

`detectSharpCurves`/`CurveVoiceEngine`은 **0715 라이딩에서 실제로 2회씩 발화한 전례가
있고**(`sharp_turn_left/right_approach/imminent`), 실측 도로 형상(고덕갈평로) 픽스처로
알고리즘 정확성도 테스트로 검증돼 있음(`test/routing_service_sharp_curve_test.dart`
케이스 C). 오늘 밤엔 재탐색이 매우 잦았던 것으로 로그에서 확인됨(수 시간에 걸친 심야+
퇴근 라이딩) — 실제 주행 경로가 원래 계획과 계속 달라졌을 가능성이 있고, `enabledEvents`
설정도 `assets/config/guidance_profile.json`에서 정상 활성화돼 있음을 확인함(코드/설정
버그 아님). **임계값(45도/100m 윈도우) 튜닝은 재현 가능한 좌표 없이는 하지 않음** —
0715 문서의 동일 원칙 유지.

**다음 라이딩에서 확인할 것**: `grep 'curve='` 결과에서 `curveZoneIdx`가 한 번이라도
-1이 아니었는지(감지는 됐지만 음성만 안 나온 것인지, 아예 감지 자체가 없었는지 구분).

### 11. 도착 시 하단 도착배너 없이 바로 내비 종료

코드 상으로는 도착배너(`_arrivalBannerVisible`)를 거치지 않고 화면을 강제 종료하는
별도 경로를 찾지 못함 — 배너 표시 조건(`prog.arrived && _passedWaypointCount >=
waypoints.length`)이 사실이 아니었을 가능성(예: 마지막 목적지가 라우팅 그래프 밖이라
`offRoute`가 계속 true였고, 반복 재탐색 실패로 `_rerouteFallback` 폴백 음성만 나가고
끝난 경우)을 포함해 여러 시나리오가 가능하나 로그 없이는 특정 불가.

**다음 라이딩에서 확인할 것**: 도착 직전 구간의 `YNAV_ARR`/`YNAV_REROUTE`/`offRoute` 값.

## ▶ 설계 판단 필요 (버그 아님)

### 1. 주행 중 내비 화면 POI가 느림 + 주유소 실시간 우선 요청

"1회 로딩 이후 동일 구간은 빠름"이라는 보고는 `PoiRegionCache`가 실제로 잘 작동한다는
뜻(캐시 히트). 문제는 캐시가 거의 항상 미스되는 **주행 중** 상황 — nav 화면의 자동 추종
모드가 GPS 위치를 중심으로 한 합성 bbox(±0.02°)를 매 fetch마다 재중심화하는 구조라,
전진 방향으로 계속 새 영역이 되어 캐시가 사실상 무력화됨(이전 code-auditor 지적).
사용자가 명시적으로 요청한 "주행 중엔 주유소만이라도 실시간 우선 탐색"은 캐시 전략과
무관한 신규 기능(카테고리별 차등 fetch 우선순위) — 범위가 있는 설계 결정이라 이번엔
보류.

### 5. 검색 시트 칩 탭 체감 속도

칩 탭 자체는 이미 fetch된 결과를 클라이언트에서 필터링만 하는 구조라 네트워크 호출이
없음 — "느리다"는 체감은 시트를 연 직후의 최초 1회 fetch(1500m 반경, 전체 카테고리)가
아직 끝나기 전에 칩을 눌러서 로딩 중인 상태를 보고 있을 가능성이 높음. 오늘 밤 수정한
서버 쿼리플랜(`CROSS JOIN`)+응답 캡(`MAX_POI_RESULTS`)으로 이 최초 fetch 자체는
빨라졌지만(2.3~2.5s → ~1.0s), Cloudflare Tunnel 왕복 자체가 ~0.55s 바닥이라 완전히
"즉시"는 아님. 로딩 중 칩 탭 시 스피너/비활성화 같은 UX 처리가 필요한지는 설계 판단
필요.

성공(zones 조회 자체는 안정적으로 200 응답). 다만 테스트에 쓴 경로들이 전부 `zones=0`

음성이 나오는지까지는 확인 못 했다** — 6-잔여(`minLengthM=100` 가설)는 여전히 미확정.
다음 라이딩에서 실제 터널/고가 통과 시 `zones=`가 0이 아닌지, 그런데도 음성이
없는지를 봐야 최종 결론이 난다.

### 11. 도착배너 — **근본원인 확정 + 수정 완료(커밋 `da80403`)**

정지 상태(0km/h)로 목적지 반경 안에 들어오면 `exitGateOpen()` 조건(30m 이내+
30km/h 이하)이 사실상 즉시 열리고, 그 순간부터 10초 자동종료 타이머가 시작됨.

눌리는 "종료" 버튼과, 작은 우상단 X 아이콘뿐. 실제로 두 번의 가상 GPS 재현에서 모두
정확히 타이머 종료 시점(발화 후 약 10초)에 내비 화면이 홈 화면으로 조용히 닫히는 걸
확인했다(로그상 위젯 범위 로그 `YNAV_TTS`/`YNAV_GUIDE`/`YNAV_REROUTE`가 멈추고,

`routeProgressProvider`가 계속 살아있다는 뜻이라 별도의 사소한 자원 누수이긴 하나
이번엔 손대지 않음). 실제 라이더가 헬멧을 벗거나 정차 처리를 하는 등 10초 안에 화면을

**수정**: 배너 버튼 행에 "계속 안내"(항상 탭 가능, 타이머 취소 + 배너만 닫음) 버튼을
