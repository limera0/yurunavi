# 2026-07-16 가상 GPS 60회 주행 테스트 — 고가/지하차도/터널 진입 시 "우측 출구" 오안내 검증

사용자가 지정한 6개 구간(언더패스 진입/옆길, 고가도로 진입/옆길, 터널 진입/옆길) × 10개
속도(30~120km/h, 10km/h 단위)로 총 60회 가상 GPS 주행을 자동화 실행한 결과.

## 요약

- **속도와는 무관함이 확정됨** — 같은 구간이면 30km/h든 120km/h든 발화하는 이벤트(맨뉴버
  타입, 구조물 zone 개수, TTS 키 목록)가 완전히 동일. Valhalla가 경로/maneuver를 미리
  계산해두는 구조라 실시간 속도가 "우측 출구"를 유발/억제하지 않음.
- **짧은 구간(언더패스/고가도로) "진입" 경로는 전부 깨끗함** — 구조물을 직진으로 통과하는
  경로에서는 10회 전부 "우측 출구"(맨뉴버 타입 20)가 전혀 발화하지 않음.
- **짧은 구간 "옆길" 경로는 실제로 우회전 출구가 1회씩 있음** — 이건 버그가 아니라 정상:
  본선에서 벗어나 옆길로 가려면 실제로 우측 분기가 있으니 "우측 출구"가 나오는 게 맞음.
- **긴 터널 구간(진입/옆길 둘 다)에서 "우측 출구"가 2회씩 발화** — 위치를 특정해보니 1회는
  출발 직후(터널과 무관), 1회는 도착 직전 두 개의 연속 터널을 통과한 직후(터널 안내와
  시간상 겹침). 이게 사용자가 느낀 "터널 들어가는데 우측 출구라고 한다"는 체감과 가장
  가까운 사례로 보이나, **실제 도로에 진짜 나들목이 있을 가능성이 높아 완전한 오분류로
  단정하지는 못함** — 아래 §3 참조.

## 0. 테스트 인프라 (이번 세션에서 구축, 재사용 가능)

기존에 있던 `gpsinjector`(가상 GPS 재생 전용 별도 앱)에 더해, 앱 쪽에 디버그 전용 자동
주행 하네스를 추가함:

- `android/app/.../MainActivity.kt` + `lib/features/map/presentation/main_map_screen.dart`:
  `adb shell am start ... --es e2e_dest_lat <lat> --es e2e_dest_lon <lon>`로 목적지를
  주면, `kDebugMode`에서만 동작하는 하네스가 실제 지도 탭과 동일한 경로(목적지 설정 →
  경로 계산 대기 → 내비 자동 시작)를 그대로 밟는다. 릴리스 빌드에서는 `kDebugMode`가
  컴파일타임 상수라 완전히 제거됨.
- `route_gen.py`(스크래치패드): Valhalla `/route`를 앱과 동일한 costing_options(국도,
  `selectedRouteIdx=2` 기본값)로 호출해 실제 경로 shape를 가져오고, 지정 속도로 1Hz
  리샘플링해 `gpsinjector`가 재생할 CSV(seq,lat,lon,speed_mps,bearing_deg,accuracy_m,
  delay_ms)를 생성. 출발 직후 8초간 원점에 정지 상태로 고정해두는 것도 포함 —
  앱이 실행되는 타이밍에 따라 원점 GPS fix를 놓치면 앱 자체 경로 계산이 스크립트가
  가져온 경로와 미묘하게 어긋나는 문제가 있어 추가함.
- `run_all.sh`: 60개 조합을 순회하며 CSV 생성 → push → 두 앱 강제 재시작 →
  `gpsinjector` 재생 시작 → `yurunavi` 하네스로 목적지 지정 → logcat 캡처 →
  요약(`results/summary.tsv`) 저장까지 전부 자동화.

### 도중에 발견한 중대 버그: Android FUSED_PROVIDER의 실측 위치 누출

`gpsinjector`가 `GPS_PROVIDER`만 모킹했을 때, **매 60~100초 간격으로 실제(mocked=false)
위치 fix 1개가 앱에 그대로 전달**되는 현상을 발견함. 이 실측 fix는 항상 동일한 좌표
(약 37.0732, 127.0477 — 이 서버/사무실의 실제 물리적 위치로 추정, Wi-Fi 기반 정확도
20m)였고, 정확히 그 순간 라이더 앱이 "그 실측 좌표에서 경로 shape상 가장 가까운
지점"으로 스냅해버려 — 마침 그 실측 좌표가 경로의 목적지 근처 shape 포인트와 우연히
가장 가까웠던 탓에 — **가짜 도착 판정 + 연쇄 재탐색**이 발생했다. `NETWORK_PROVIDER`도
같이 모킹해도, `Geolocator`의 `forceLocationManager`(Play Services 우회)를 켜도
안 없어졌고, 최종적으로 **Android 12+(API 31+)에서 추가된 `LocationManager.
FUSED_PROVIDER`("fused")** — GPS/NETWORK와 별개인 OS 레벨 3번째 provider — 까지
같이 모킹하고 나서야 완전히 사라짐(`YNAV_FIX` 진단 로그로 `mocked=false` 발생이 0으로
확인됨).

이건 **테스트 인프라 버그이지 실제 라이더 앱의 버그는 아님** — 실제 주행에서는 GPS
위성 신호가 항상 우세해서 이런 네트워크/퓨즈드 fallback이 끼어들 일이 거의 없다. 다만
가상 GPS로 이 앱을 테스트하려는 향후 세션은 반드시 이 3-provider 모킹 방식을 그대로
써야 함(안 그러면 60~100초마다 알 수 없는 오프루트/재탐색이 섞여 데이터가 오염됨 —
실제로 이번 세션에서 1차 60회 전량을 이 버그 때문에 폐기하고 재실행함).

## 1. 짧은 구간 결과 (언더패스·고가도로)

| 구간 | 우측출구(타입20) | 구조물zone | 비고 |
|---|---|---|---|
| 언더패스 진입 (10회) | 0/10 | tunnel×1 | 깨끗함 — `tunnel_approach/imminent`만 정상 발화 |
| 언더패스 옆길 (10회) | 1/10(매회) | 없음 | `exit_approach_landmark`+`turn_right_*` — 본선 이탈용 정상 우회전 |
| 고가도로 진입 (10회) | 0/10 | bridge×1 | 깨끗함 — `bridge_imminent`만 정상 발화 |
| 고가도로 옆길 (10회) | 1/10(매회) | 없음 | `sharp_turn_left_*` 계열 — 좌회전 분기, "우측 출구"와 다른 케이스 |

이 4개 구간에 한해서는 **"구조물을 직진 통과하는데 우측 출구라고 나온다"는 재현에
실패**했다 — 오히려 정확히 기대대로 동작함(직진 통과=구조물 안내만, 옆길 진입=해당
방향 분기 안내).

## 2. 긴 터널 구간 결과

| 구간 | 우측출구(타입20) | tunnel_imminent | bridge_imminent |
|---|---|---|---|
| 터널 진입 (10회) | 2/10(매회) | 4~5 | 3 |
| 터널 옆길 (10회) | 2/10(매회) | 4 | 3 |

진입/옆길 두 목적지가 경로 후반부에서만 갈라지고 대부분 구간을 공유하기 때문에,
두 "우측 출구" 이벤트는 사실상 **공유 구간에서 발생**한다(목적지 분기와 무관).

### 우측출구 #1 — 출발 약 150~250m 지점 (37.6806~37.6811, 126.8931~126.8948)
구조물 안내(`tunnel_approach`)가 아직 시작되기 전에 발화. 터널/교량과 무관한, 그냥
출발 직후 첫 나들목으로 보임 — 사용자가 보고한 증상과 무관해 보임.

### 우측출구 #2 — 도착 약 300~600m 전 (37.5695~37.5734, 126.8950~126.8988)
**이게 사용자 증상과 가장 가까운 사례.** 실측 로그(`tunnel_entry_60`) 타임라인:

```
17:21:27  tunnel_approach zone=5  (500m)
17:21:56  exit_approach dist=1000 step=7   ← "우측 출구" 카운트다운 시작
17:21:58  tunnel_imminent zone=5           ← 터널 진입
17:22:13  tunnel_approach zone=6  (300m)   ← 바로 다음 터널 접근
17:22:29  tunnel_imminent zone=6           ← 두 번째 터널 진입
17:22:57  exit_imminent dist=10 step=7     ← "우측 출구" 임박 (터널 진입 26초 후)
17:22:58  maneuver=20 시작(우측 출구)
```

연속된 두 터널을 빠져나온 지 26초 만에 "우측 출구" 안내가 임박 단계로 들어간다 —
라이더 입장에서는 "터널에서 나오자마자 출구라고 한다"로 체감될 수 있는 타이밍이다.
다만 **좌표(37.573, 126.899 부근)를 실제 지도/OSM에서 확인하지 않고는 이게 진짜
나들목(정상 안내)인지, Valhalla가 도로 분류를 잘못 인식한 가짜 분기인지 이 세션에서는
결론 내리지 못했다** — 10회 전부(30~120km/h) 완전히 동일한 위치·순서로 재현되는 걸
보면 GPS 노이즈나 우연이 아니라 이 도로망 자체의 결정론적 특성.

## 3. 다음에 확인할 것

1. `docker exec yurunavi-valhalla`나 `trace_attributes`로 좌표 (37.573,126.899) 부근
   OSM way 태그를 직접 조회 — 실제 나들목(고속도로 exit ramp)이 있는지, 아니면
   본선과 나란히 붙은 측도/접속로가 "exit"로 오분류된 것인지 확인.
2. 만약 진짜 나들목이면 버그가 아니라 "터널 통과 직후 안내가 몰려서 혼란스럽다"는
   UX 이슈로 재분류 — 터널 안내와 다음 maneuver 안내 사이에 최소 간격을 두는 안이
   필요할 수 있음(예: 구조물 임박 안내 후 N초는 다른 안내를 지연).
3. 짧은 구간 4개는 이번 테스트로는 재현 실패 — 사용자가 실제로 "우측 출구"를 들은
   정확한 지점(좌표)이 있다면 그 좌표로 재테스트 필요.
